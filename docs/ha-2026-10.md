# Home Assistant 2026.10 migration and recovery

[English](ha-2026-10.md) | [Català](ha-2026-10.ca.md) | [Español](ha-2026-10.es.md)

Runxin Local **2.10.0 requires HA 2026.10.0+** and uses `python-broadlink>=1.0.6`, matching HA's official BroadLink integration. Earlier HA versions should retain Runxin Local 2.9.3. Physical G6 readings and field-10 writes were confirmed on 2026-10-12 after rebuilding Core; see the scoped validation below.

## Why the dependency changes

HA 2026.9 used the synchronous `broadlink==0.19.0` distribution; HA 2026.10 uses async `python-broadlink`. Both install the import module `broadlink`, so installing the old distribution can overwrite the new files while package metadata still says the new dependency is installed. This is the conflict reported in [issue #33](https://github.com/Danirv/runxin-local/issues/33) and [Core #184800](https://github.com/home-assistant/core/issues/184800).

All network paths, including the built-in read-only collector, now await the async library. Endpoint cleanup, bounded reads, model permissions and physical read-back remain explicit. Writes use a per-device single-datagram adapter because the library's public send method can retransmit on silence or reauthenticate/replay. There is no global library patch. Field codecs, conversions, domain `ypsilon_local`, config-entry version, entity IDs and existing model support levels are preserved.

## Upgrade and already overwritten installations

The recovery step depends on the installation's history:

- **HA 2026.10 has already run Runxin Local 2.9.3 or earlier, or another integration requiring old `broadlink`:** first update Runxin Local to 2.10.0 and update/remove **all** other integrations with the old requirement. On **HA OS / Supervised**, then run `ha core rebuild` from the HA CLI and let Core restart. On **Container**, recreate Core from the intended official image. This is the recommended recovery path even if the old Runxin integration appeared to work: that does not establish that Core's async BroadLink files were intact.
- **Clean installation with HA 2026.10+ and Runxin Local 2.10.0, or an existing installation with the new library intact:** install/update and restart normally. Rebuilding Core is not a universal installation requirement.
- **`cannot import name 'EndpointClosedError'` or missing/failing Core BroadLink devices:** use the recovery path above after correcting all old requirements. Replacing a requirement or restarting alone does not restore overwritten files; package metadata may still mark the new library as installed.

Keep the existing operational entry and pairing. This recovery replaces Core files; it is not a device factory reset or a migration of the `ypsilon_local` domain. Afterwards, check both Runxin Local and any official BroadLink devices. Do not manually uninstall/install packages inside HA's managed environment; an old requirement left in another integration could overwrite the files again.

## Physical G6 validation

The automated suite covers HA 2026.10.0/2026.10.1, existing model regressions, real library authentication/AES with a loopback UDP peer, single-datagram writes under timeout/outer error, cancellation, raw read-only scans and Core BroadLink device coexistence. It cannot prove physical acceptance on a G6.

### Maintainer result: 2026-10-12

On **2026-10-12**, the maintainer validated **Runxin Local 2.10.0 on HA 2026.10.1 / HA OS 18.3**, against the physical **ATH/BWT Ypsilon G6, controller model 9, BL3372 `0x520F`, firmware 62016**. The installation had previously run HA 2026.10 with Runxin Local 2.9.3; Core was rebuilt before this validation.

The diagnostic snapshot reports a ready/available connection, a successful poll in **813.7 ms**, zero recorded failed polls, retries or reauthentications, and raw pairs for fields 1–52. The snapshot does not establish that all fields were queried afresh in that poll; field 52 can be cached. The maintainer also changed the **regeneration trigger time (field 10) from HA and confirmed it in the manufacturer app**, then changed it in the app and confirmed the refresh in HA. This establishes physical readings and field-10 write acceptance with the new async transport after Core recovery.

This observation does not establish that updating/restarting without rebuilding would have repaired that installation. Other writes retain their earlier per-field evidence; they were not retested with the async transport in this report. Regeneration-start commands, prolonged operation, reload/restart recovery and physical coexistence with other Core BroadLink devices were not newly validated. No model support level or write permission changes follow from this report.

### Further device checks

An isolated read-only check does **not require updating your working HA installation**. On a separate computer with Python 3.13+ and the full v2.10.0 checkout:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install python-broadlink==1.0.6
.venv/bin/python scripts/validate_async_connection.py DEVICE_IP --output runxin_async_report.json
```

Replace `DEVICE_IP` locally. The script reads discovery/authentication, firmware and fields 1–52. It never changes settings, clock, regeneration or pairing. Its JSON omits identifiers, keys and raw packets; exit 2 means a partial/failed report, which is still useful. Pause other polling clients for the check if they interfere, and resume them afterwards. Compare fresh values/raw pairs with existing G6 diagnostics and visible app readings.

After that read check, validate the v2.10.0 integration in HA 2026.10+: ordinary polling, existing entity identities, an ordinary reload/restart and the official BroadLink entities, if present. For an additional reversible write check, use a permitted setting such as regeneration trigger time (field 10) or the device clock (field 4), recording baseline → requested value → fresh HA read-back → app/controller → restored value. The maintainer's field-10 test already confirms write delivery on the reference G6; a clock test is not additionally required to establish that basic transport capability. No regeneration is needed to validate this migration. Report read results and write results separately; previous hardware evidence does not automatically certify the new transport.

Once an installation has actually upgraded to 2.10.0, returning to 2.9.3 on HA 2026.10 can reintroduce the old dependency collision. Restore a compatible HA/integration combination if rolling back.
