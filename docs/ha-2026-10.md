# Home Assistant 2026.10 migration and recovery

[English](ha-2026-10.md) | [Català](ha-2026-10.ca.md) | [Español](ha-2026-10.es.md)

Runxin Local **2.10.0 requires HA 2026.10.0+** and uses `python-broadlink>=1.0.6`, matching HA's official BroadLink integration. Earlier HA versions should retain Runxin Local 2.9.3. The new transport is under validation; automated tests and loopback UDP are not physical BL3372 evidence.

## Why the dependency changes

HA 2026.9 used the synchronous `broadlink==0.19.0` distribution; HA 2026.10 uses async `python-broadlink`. Both install the import module `broadlink`, so installing the old distribution can overwrite the new files while package metadata still says the new dependency is installed. This is the conflict reported in [issue #33](https://github.com/Danirv/runxin-local/issues/33) and [Core #184800](https://github.com/home-assistant/core/issues/184800).

All network paths, including the built-in read-only collector, now await the async library. Endpoint cleanup, bounded reads, model permissions and physical read-back remain explicit. Writes use a per-device single-datagram adapter because the library's public send method can retransmit on silence or reauthenticate/replay. There is no global library patch. Field codecs, conversions, domain `ypsilon_local`, config-entry version, entity IDs and existing model support levels are preserved.

## Upgrade and already overwritten installations

For an ordinary upgrade on HA 2026.10+, update the integration and restart HA. Keep the existing operational entry; no deletion, re-pairing or domain migration is required.

If logs show `cannot import name 'EndpointClosedError'` or Core BroadLink devices disappeared, first update/remove **all custom integrations still requiring the old `broadlink` distribution**, including Runxin Local versions before 2.10.0. Simply replacing the requirement or restarting does not restore files already overwritten: package metadata may incorrectly satisfy the new dependency.

On **HA OS / Supervised**, after addressing those old requirements, run `ha core rebuild` from the HA CLI and let Core restart. On **Container**, recreate Core from the intended official image. Afterwards, check both Runxin Local and the official BroadLink devices. Do not manually uninstall/install packages inside HA's managed environment; another old requirement could overwrite the files again.

## Physical G6 validation

The automated suite covers HA 2026.10.0/2026.10.1, existing model regressions, real library authentication/AES with a loopback UDP peer, single-datagram writes under timeout/outer error, cancellation, raw read-only scans and Core BroadLink device coexistence. It cannot prove physical acceptance on a G6.

An isolated read-only check does **not require updating your working HA installation**. On a separate computer with Python 3.13+ and the full v2.10.0 checkout:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install python-broadlink==1.0.6
.venv/bin/python scripts/validate_async_connection.py DEVICE_IP --output runxin_async_report.json
```

Replace `DEVICE_IP` locally. The script reads discovery/authentication, firmware and fields 1–52. It never changes settings, clock, regeneration or pairing. Its JSON omits identifiers, keys and raw packets; exit 2 means a partial/failed report, which is still useful. Pause other polling clients for the check if they interfere, and resume them afterwards. Compare fresh values/raw pairs with existing G6 diagnostics and visible app readings.

After that read check, validate the v2.10.0 integration in HA 2026.10+: ordinary polling, existing entity identities, an ordinary reload/restart and the official BroadLink entities, if present. A separate reversible manual clock check should record baseline → requested value → fresh HA read-back → app/controller → restored clock. No regeneration is needed to validate this migration. Report read results and write results separately; previous hardware evidence does not automatically certify the new transport.

Once an installation has actually upgraded to 2.10.0, returning to 2.9.3 on HA 2026.10 can reintroduce the old dependency collision. Restore a compatible HA/integration combination if rolling back.
