# Home Assistant 2026.10 migration and recovery

[English](ha-2026-10.md) | [Català](ha-2026-10.ca.md) | [Español](ha-2026-10.es.md) · [Documentation](index.md)

Runxin Local **2.10.1 and later require HA 2026.10.0+** and uses `broadlink-async>=1.1.0`, imported as `broadlink_async`. HA's official BroadLink integration uses the same namespace from **2026.10.2**. Earlier HA versions should retain Runxin Local 2.9.3. The physical G6 record below belongs to 2.10.0; it is not a new hardware test of 2.10.1.

## Dependency history

| Consumer | Distribution | Import module |
|---|---|---|
| HA 2026.9.4 / Runxin Local up to 2.9.3 | `broadlink==0.19.0` | `broadlink` |
| HA 2026.10.0–2026.10.1 / Runxin Local 2.10.0 | `python-broadlink` 1.0.6 (Runxin requirement `>=1.0.6`) | `broadlink` |
| HA 2026.10.2 / Runxin Local 2.10.1 | `broadlink-async` 1.1.0 (Runxin requirement `>=1.1.0`) | `broadlink_async` |

The first two distributions shared a directory, so an old requirement could overwrite the async library while package metadata still marked it as installed. [Issue #33](https://github.com/Danirv/runxin-local/issues/33) and [Core #184800](https://github.com/home-assistant/core/issues/184800) describe the failure. [Core PR #186053](https://github.com/home-assistant/core/pull/186053), released in HA 2026.10.2, moves Core to a separate namespace. Runxin Local 2.10.1 makes the same move. `python-broadlink` remains at 1.0.6; a requirement of `python-broadlink>=1.0.6` does not select the renamed distribution.

## Upgrade and recovery

- **Updating Runxin Local to 2.10.1:** update through HACS/manual installation and restart HA. The new dependency installs into its own directory, so this migration alone does not require `ha core rebuild`, even if the previous `broadlink` module was overwritten. Keep the operational entry, pairing, entity IDs and `ypsilon_local` domain.
- **Official BroadLink on HA 2026.10.2 or later:** Core also uses the separate namespace. Updating to 2026.10.2 fixes this specific shared-directory failure for the official integration by installing the new module; it does not repair the old module used by Runxin Local 2.10.0 or another custom integration. Update Runxin as well.
- **Staying on HA 2026.10.0/2026.10.1:** Runxin Local 2.10.1 uses the isolated namespace, but the official integration still uses `python-broadlink`. If Core BroadLink is already broken, first update/remove all custom integrations requiring legacy `broadlink`, then run `ha core rebuild` on HA OS / Supervised, or recreate the official Core container on Container installations. A normal restart cannot restore overwritten files. Alternatively, upgrade HA to 2026.10.2+.
- **Keeping Runxin Local 2.10.0:** it still imports the shared `broadlink` module, even on HA 2026.10.2. If that module was overwritten, use the earlier recovery procedure or migrate Runxin to 2.10.1. The new Core namespace does not isolate an unchanged custom integration.

After updating, check Runxin readings and any official BroadLink devices. No factory reset, re-pairing, manual package uninstall or manipulation of HA's managed Python environment is needed for the namespace migration. If another integration still depends on legacy `broadlink`, its own compatibility remains that integration's responsibility.

## Transport guarantees

All device I/O and the compatibility collector remain async. Writes still use one UDP datagram without automatic replay/reauthentication and retain independent read-back reconciliation. Per-device reply checks, endpoint cleanup, field-52 cache, codecs, conversions, permissions and model support levels are unchanged. The write adapter's framing/endpoint interface is revalidated against `broadlink-async` 1.1.0; it is not a global library patch.

## Physical G6 validation

The automated suite covers HA 2026.10.0/2026.10.2, existing model regressions, real library authentication/AES with a loopback UDP peer, single-datagram writes under timeout/outer error, cancellation, raw read-only scans and Core BroadLink device coexistence. It cannot prove physical acceptance on a G6.

### Maintainer result: 2026-10-12

On 2026-10-12, the maintainer confirmed physical G6 readings and field-10 writes with Runxin Local 2.10.0 on HA 2026.10.1 after rebuilding Core. This is dated evidence for that version/installation, not a claim that every write or the later isolated namespace was physically retested. The full device, snapshot and bidirectional app comparison are recorded in [hardware verification](hardware-verification.md#async-transport-2100-physical-g6-observation).

### Further device checks

An isolated read-only check does **not require updating your working HA installation**. On a separate computer with Python 3.13+ and the full v2.10.1 checkout:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install broadlink-async==1.1.0
.venv/bin/python scripts/validate_async_connection.py DEVICE_IP --output runxin_async_report.json
```

Replace `DEVICE_IP` locally. The script reads discovery/authentication, firmware and fields 1–52. It never changes settings, clock, regeneration or pairing. Its JSON omits identifiers, keys and raw packets; exit 2 means a partial/failed report, which is still useful. Pause other polling clients for the check if they interfere, and resume them afterwards. Compare fresh values/raw pairs with existing G6 diagnostics and visible app readings.

After that read check, validate the v2.10.1 integration in HA 2026.10+: ordinary polling, existing entity identities, an ordinary reload/restart and the official BroadLink entities, if present. For an additional reversible write check, use a permitted setting such as regeneration trigger time (field 10) or the device clock (field 4), recording baseline → requested value → fresh HA read-back → app/controller → restored value. The maintainer's field-10 test already confirms write delivery on the reference G6; a clock test is not additionally required to establish that basic transport capability. No regeneration is needed to validate this migration. Report read results and write results separately; previous hardware evidence does not automatically certify the new transport.

Rolling Runxin back to 2.10.0 restores the shared import namespace. Runxin 2.9.3 can also affect official BroadLink on HA 2026.10.0/1. Restore a compatible HA/integration combination if rolling back.
